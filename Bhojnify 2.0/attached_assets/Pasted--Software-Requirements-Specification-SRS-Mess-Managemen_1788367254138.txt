# Software Requirements Specification (SRS)
## Mess Management System

## 1. Introduction
### 1.1 Purpose
This Software Requirements Specification (SRS) details the functional and non-functional requirements for the Mess Management System. It serves as a comprehensive guide for developers, stakeholders, and mess administrators.

### 1.2 Intended Audience
This document is intended for the development team, project managers, and mess owners who will utilize the system.

### 1.3 Product Scope
The system is a web-based application designed to manage student meal plans, track daily attendance securely, and handle billing. Future iterations will include inventory, staff, and vendor management to provide an all-in-one ERP solution for mess owners.

## 2. Overall Description
### 2.1 Product Functions
**Current Functions (Implemented):**
*   User registration and authentication (WebAuthn).
*   Biometric and Geo-fenced attendance marking.
*   Meal plan management (credits and types).
*   Leave application and tracking.
*   Basic payment recording.
*   Admin and Student dashboards.

**Planned Functions (To Be Implemented):**
*   Inventory and stock control.
*   Staff attendance and payroll.
*   Menu scheduling and student feedback.
*   Comprehensive expense tracking and P&L reporting.
*   Digital notice boards and notification systems.
*   Supplier and purchase order management.

### 2.2 User Classes
*   **Student**: End-users who consume meals, apply for leaves, and pay fees.
*   **Admin / Mess Owner**: Super-users who manage users, monitor attendance, track finances, and (in the future) manage inventory and staff.
*   **Staff (Planned)**: Cooks and servers who may have restricted access to view daily headcount requirements.

### 2.3 Operating Environment
*   **Client**: Modern web browsers (Chrome, Safari, Firefox) on desktop and mobile devices. Mobile hardware is required for GPS and biometric (WebAuthn) features.
*   **Server**: Node.js runtime environment.
*   **Database**: MongoDB hosted locally or via MongoDB Atlas.

## 3. Specific Requirements

### 3.1 Functional Requirements (Current System)
*   **REQ-1.1 (Auth)**: The system shall allow users to authenticate using WebAuthn (biometrics/device PIN).
*   **REQ-1.2 (Attendance)**: The system shall record attendance only if the user's GPS coordinates fall within the predefined mess location radius.
*   **REQ-1.3 (Device Fingerprinting)**: The system shall log device fingerprints to prevent users from proxy-marking attendance on multiple accounts from the same device.
*   **REQ-1.4 (Meal Slots)**: The system shall enforce meal slot timings; attendance cannot be marked outside active slots.
*   **REQ-1.5 (Leaves)**: The system shall allow students to apply for leaves; meal credits shall not be deducted on approved leave days.
*   **REQ-1.6 (Payments)**: Admins shall be able to record payments against a student's profile, updating their membership status and validity.

### 3.2 Functional Requirements (Planned Features for Mess Owners)
*   **REQ-2.1 (Inventory)**: Admins shall be able to add, update, and remove raw ingredients from the digital stock ledger.
*   **REQ-2.2 (Stock Alerts)**: The system shall automatically flag items that drop below a set minimum quantity.
*   **REQ-2.3 (Menu Planning)**: Admins shall be able to assign specific dishes to meal slots up to 4 weeks in advance.
*   **REQ-2.4 (Feedback)**: Students shall be able to rate a consumed meal on a scale of 1-5 and leave optional text feedback.
*   **REQ-2.5 (Staff Management)**: The system shall maintain staff profiles including salary details and role.
*   **REQ-2.6 (Expenses)**: Admins shall be able to log daily miscellaneous expenses categorized by type (e.g., Gas, Transport, Maintenance).
*   **REQ-2.7 (Reporting)**: The system shall generate a monthly financial report contrasting revenue from payments against expenses and inventory costs.
*   **REQ-2.8 (Notifications)**: The system shall send automated reminders to students whose membership is within 3 days of expiry.

### 3.3 Non-Functional Requirements
*   **Performance**: The attendance marking API must respond within 500ms to avoid queues at the mess entrance.
*   **Security**: All passwords (if any) must be hashed. WebAuthn credentials must be stored securely. User location data must not be tracked outside of the explicit attendance marking event.
*   **Availability**: The system should target 99.9% uptime, especially during active meal slots.
*   **Scalability**: The database architecture must support up to 10,000 daily attendance records without performance degradation.
